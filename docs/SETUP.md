# Setup — one-time steps for the repo owner

Follow these in order. Steps (a)–(c) are in Meta's world, (d) is in GitHub,
(e) is the test flight. Budget about 30 minutes.

## (a) Confirm the Instagram account qualifies

The Graph API can only publish to a **Business or Creator** Instagram
account that is **linked to a Facebook Page**.

1. In the Instagram app, open the `@deanzachessclub` profile → menu →
   **Settings → Account → Switch to professional account** if it still says
   personal. (If it already says Business/Creator, skip this.)
2. In the same place, link the account to the club's Facebook Page
   (**Settings → Accounts Centre → Pages → Add** the page). If the club has
   no Facebook Page yet, create one first — the API requires it even though
   nothing is ever posted to Facebook.

If the account cannot be switched/linked, stop here: Graph API publishing
will not work, and the fallback is the browser-automation route instead.

## (b) Create a Meta developer app

1. Go to <https://developers.facebook.com/apps> → **Create App** →
   choose **Other** → type **Business**.
2. In the app dashboard, **Add Product** → **Instagram Graph API**
   (listed under "Instagram"). Complete any required app review prompts for
   development use — for posting to your own account, no full App Review is
   needed while the app is in development mode, but the token below must be
   generated by a user with a role on the app (Admin/Developer/Tester).
3. In **App Settings → Basic**, note the **App ID** and **App Secret** —
   you need them for the token exchange in step (c).

## (c) Get the IG user ID and a long-lived access token

Do this in a terminal (replace the placeholders) or in the
[Graph API Explorer](https://developers.facebook.com/tools/explorer/).

**1. Short-lived user token.** In Graph API Explorer, select your app, click
**Generate Access Token**, and grant these permissions:

- `instagram_basic`
- `instagram_content_publish`
- `pages_read_engagement` (needed to read the Page → IG account link)

**2. Exchange it for a long-lived token** (valid ~60 days; set a calendar
reminder to refresh it):

```bash
curl -G "https://graph.facebook.com/v21.0/oauth/access_token" \
  --data-urlencode "grant_type=fb_exchange_token" \
  --data-urlencode "client_id=<APP_ID>" \
  --data-urlencode "client_secret=<APP_SECRET>" \
  --data-urlencode "fb_exchange_token=<SHORT_LIVED_TOKEN>"
```

The response contains `access_token` — that is the long-lived token.

**3. Find the Instagram user ID:**

```bash
# List Pages this user manages:
curl "https://graph.facebook.com/v21.0/me/accounts?access_token=<LONG_LIVED_TOKEN>"

# For the club's Page, get the linked IG account (replace <PAGE_ID>):
curl "https://graph.facebook.com/v21.0/<PAGE_ID>?fields=instagram_business_account&access_token=<LONG_LIVED_TOKEN>"
```

The `instagram_business_account.id` value is the **IG user ID** (numeric).

> **Token expiry:** long-lived user tokens last about 60 days. Before one
> expires, re-run the exchange in step 2 with a fresh short-lived token and
> update the `IG_ACCESS_TOKEN` secret. If a scheduled run starts failing
> with `OAuthException` / "Session has expired", an expired token is the
> first thing to check.

## (d) Add the repo secrets

In the GitHub repo: **Settings → Secrets and variables → Actions →
New repository secret**, add both:

| Name | Value |
|---|---|
| `IG_USER_ID` | numeric ID from step (c) |
| `IG_ACCESS_TOKEN` | long-lived token from step (c) |

Never commit either value to the repo. The workflows read them only from
secrets at run time.

## (e) Test flight

1. **Dry run (nothing posts):** Actions → **Publish weekly puzzle
   question** → **Run workflow** → leave `dry_run` checked → Run. Check
   the logs: `prepare` should render the next queued puzzle and `post`
   should print the `DRY RUN — nothing posted` banner. Repeat for the
   answer workflow.
2. **Live manual post:** run the same workflow with `dry_run` **unchecked**.
   It posts for real to @deanzachessclub and updates `data/queue.json`.
   Do this once, verify the post on Instagram, and confirm the queue commit
   landed on `main`.
3. **Let the schedule take over.** The cron runs Mon/Thu at 09:00 PT
   (question) and 16:00 PT (answer). From this point the old
   browser/cron system must be stopped — running both at once would post
   the same puzzle twice. See the cutover note in the README.
